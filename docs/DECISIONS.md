# Decision log

Each row: what we chose, what else we considered, why, and what it costs us.

| # | Decision | Alternatives | Why | Trade-off |
|---|---|---|---|---|
| 1 | **React + Vite + TypeScript** on the client, **Node + Express + TypeScript** on the server, in one repo (`client/`, `server/`) | Angular; Next.js full-stack; plain JS | The assignment asks for React and the role is React + Node. One language end to end. Types document the data shapes shared by client and server | TypeScript adds syntax; types are duplicated between client and server instead of shared from a package (fine at this size) |
| 2 | **PostgreSQL on Neon** via **Prisma** | MongoDB Atlas; SQLite; Render Postgres | Relational data (users → preferences → feedback) with uniqueness rules the DB enforces. Neon's free tier doesn't expire (Render's free Postgres is deleted after 30 days). Prisma gives a readable schema file and typed queries | Prisma is an extra abstraction over SQL; Neon cold-starts after idle |
| 3 | **JWT in an httpOnly cookie**, API called on the **same origin** (Vite proxy locally, Vercel rewrite `/api/*` → Render in production) | JWT in localStorage + `Authorization` header; server sessions | Page JavaScript can't read an httpOnly cookie, so an XSS bug can't steal the token. Same origin means `SameSite=Lax` works and no CORS setup is needed | No server-side session list, so a token can't be revoked before it expires (7 days). Acceptable for this scope |
| 4 | **Feature modules** on the server (`modules/auth/{routes,controller,service,schemas}`) | One folder per layer (`routes/`, `controllers/`, `services/`) | Everything about one feature sits together. Inside a module the layers are still separate: routes wire middleware, controllers translate HTTP, services hold logic and talk to the DB | Slightly more files per feature |
| 5 | **zod** validation at the API boundary (`validateBody` middleware) and for env vars (`config/env.ts`) | Manual checks; express-validator | One schema both validates and produces the TypeScript type. Bad env fails at startup, not on the first request | One more library |
| 6 | **One error shape**: services throw `HttpError(status, message)`; one `errorHandler` writes `{ error, details? }` | try/catch + `res.status()` in every controller | No duplicated error code. The client has one `ApiError` to handle | None significant |
| 7 | **Same 401 for a wrong email and a wrong password** | Separate "user not found" message | Doesn't reveal which emails have accounts (user enumeration) | Slightly less helpful message |
| 8 | "Onboarding done" = **a `Preferences` row exists** | A boolean `onboarded` flag on `User` | One source of truth; a flag could drift out of sync with the data | None |
| 9 | **TanStack Query** for server data on the client | `useEffect` + `useState` fetching; Redux | Caching, loading/error states and retries without hand-written effects (HiWay lesson: no `useEffect` that doesn't need to exist). The signed-in user lives in the query cache, so login/logout update every guard at once | A library to learn; `staleTime`/cache keys need care |
| 10 | **Route guards as layout routes** (`RequireAuth`, `GuestOnly`) | Checks inside every page | Pages don't know about auth; the redirect rules live in one file and are tested | None |
| 11 | **Tailwind CSS** | CSS Modules; a component library (MUI) | Fast to build a clean, consistent UI; no separate stylesheet per component | Long class strings in JSX; repeated patterns are extracted into components (`Button`, `TextField`) |
| 13 | **Infrastructure as config**: `render.yaml` Blueprint for the API, `client/vercel.json` for the rewrite; Render and Neon both in Frankfurt; migrations run in the Render build | Clicking settings by hand in each dashboard | The deploy setup is versioned and reviewable in the repo. Same region keeps API → DB latency low | Render's free tier sleeps after 15 min idle (first request about 50 s) |
| 14 | **The server owns the quiz options** (`preferences.catalog.ts`, served at `GET /api/preferences/options`); the same list validates `PUT /api/preferences` | Hard-coding the coins and labels in the React page | One source of truth: the choices the UI shows and the values the API accepts can't drift apart. `Record<InvestorType, …>` makes the build fail if an enum value has no label | One extra request when the quiz loads |
| 15 | **The quiz is data**: a `STEPS` array (title, hint, `isAnswered`, `render`) drives one generic page; answers stay in local state and are saved in **one PUT at the end** | One component per step; saving after every step | No duplicated step/navigation code. Answers live only in the component that uses them (state low in the tree). One request means no half-finished onboarding in the DB | Leaving mid-quiz loses the answers (3 quick questions, so acceptable) |
| 16 | **Preferences saved with upsert**; duplicates dropped by the schema | Separate create and update endpoints | The same endpoint serves first-time onboarding and a later "edit preferences" | None |
| 17 | **One endpoint per dashboard section** (`/api/dashboard/{prices,news,insight,meme}`), each with its own React Query hook and card | One `/api/dashboard` call returning everything | A slow LLM or a failing news API affects one card, not the page. Each section gets its own cache policy (prices every minute, insight once a day, a new meme every visit) | 4 requests instead of 1 |
| 18 | **Providers as adapters** (`providers/*.ts`): each wraps one external API, maps its response to our own type, and owns its fallback. They return `{ source: 'live' \| 'fallback', data }` | Calling the APIs directly from services | The rest of the app never sees CoinGecko's or CryptoPanic's field names. Swapping a source changes one file. The UI can honestly label sample data | One more layer |
| 19 | **Cache-aside with stale-on-error** (`lib/cache.ts`, in memory) | No cache; Redis | Free tiers have strict rate limits (CoinGecko, CryptoPanic's monthly quota). Serving a slightly old value beats an error | Per-instance memory; several instances would need a shared cache like Redis |
| 20 | **No fake prices.** If CoinGecko fails with nothing cached, return `503` and show an error card | A static price fallback | Invented prices in a finance app are worse than "unavailable". News, insight and memes can fall back because sample content there is harmless and clearly labelled | The prices card can be empty during an outage |
| 21 | **The insight is stored once per user per day** with its prompt and model; fallbacks are never stored | Calling the LLM on every page load | "Of the day" becomes literal, LLM cost and latency are paid once, and every insight is saved with the exact prompt that produced it, which is what the training proposal needs | Changing preferences mid-day doesn't change today's insight |
| 22 | **Votes store a snapshot**: the item as displayed plus the user's preferences at vote time | Storing only `(itemId, vote)` | News and memes rotate, so an id alone wouldn't tell a future model what was shown or to whom. The snapshot makes each row a complete (context, content, reaction) training example | Some duplicated data; the snapshot is capped at 5 KB |
| 23 | **Optimistic voting with local state** in each card (`useVote`), rolled back on error | Refetching the section after every vote | The thumb responds instantly, and only that card re-renders | The local state can briefly differ from the server until the request finishes |
| 24 | **Feedback is used right away in one small way**: memes the user voted down are never shown to them again | Collecting only, using nothing until "later" | Shows the loop working end to end without pretending to have a trained model | It's filtering, not learning (the training proposal covers the real thing) |
| 25 | **Section order follows content preferences**; all 4 sections always show (insight first) | Hiding sections the user didn't pick | The spec requires all 4 sections. Ordering is a visible but safe way to personalise | None |
| 26 | **News: CryptoPanic → Cointelegraph RSS → built-in explainers.** CryptoPanic, the API the assignment suggests, **no longer has a free plan**: its API dashboard says "To start using API, please upgrade to a Paid API Plan". We keep its adapter as an optional first source (`CRYPTOPANIC_API_KEY`) and added a free, keyless RSS feed as the live source | Static fallback only (allowed by the spec, but news never looks live); CoinDesk's API (also needs a key); dropping CryptoPanic entirely | The assignment says "use only free public APIs" and allows "CryptoPanic API or static fallback". RSS honours the intent (free, live crypto news) while keeping the suggested API wired in. Adding a source was one new provider file plus one line in the news orchestrator, which validated decision 18 | RSS has no coin filter, so we tag headlines ourselves by matching coin names and tickers as whole words (`tagCoins`). A headline that mentions a coin only indirectly won't be tagged |
| 27 | **LLM calls send `reasoning: { enabled: false }`, and the free model list starts with the fastest reliable models** (Nemotron Lightning, then Nemotron Super, then Gemma) | The first free models we found (Gemma) | Testing with a real key showed both Gemma endpoints returning 429 (busy upstream), and Nemotron spending all 400 tokens on hidden "thinking", leaving an empty answer. With reasoning off, Nemotron answers in under a second. The order is config (`OPENROUTER_MODELS`), not code, because free models change | Free models can disappear; the rule-based fallback covers that |
| 12 | **Tests against a real Postgres** (Docker locally, separate `moveo_test` DB) | Mocking Prisma | Tests catch real DB behaviour (unique constraints, cascades) | Tests need Docker running |
